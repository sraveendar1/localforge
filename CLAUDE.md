# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

`localforge` is a hardware-aware orchestration tool: it profiles the user's machine, matches that hardware against a curated catalog of open-weight models, pulls/serves the best-fitting ones locally via Ollama, and lets a frontier model of the user's choice (Claude, GPT, or any LiteLLM-supported provider) act as the orchestrator — planning a task and delegating subtasks (coding, docs, and reserved future modalities like image/video generation) to those local models. The design goal is **no vendor lock-in on the frontier model side**, and cost/hardware efficiency by keeping the actual grunt work local.

## Commands

Packaged and dependency-managed with [uv](https://docs.astral.sh/uv/) (`uv.lock` is committed; `.python-version` pins 3.12 — uv fetches that Python automatically if it's not present, so a pre-installed Python is not required).

```bash
# Setup for development
uv sync --extra dev

# Run tests
uv run pytest -q
uv run pytest tests/test_catalog.py -q          # single file
uv run pytest tests/test_catalog.py::test_best_match_picks_highest_tier_that_fits -q  # single test

# CLI during development
uv run localforge scan
uv run localforge doctor    # checks Ollama + frontier API key + hardware fit (also prints detected hardware)

# Install as a standalone end-user tool (no venv activation needed afterward)
./install.sh                 # shows what it will install + waits for Enter, then bootstraps Homebrew (macOS)+uv, installs the tool, runs setup
uv tool install --reinstall . # re-run manually after changing dependencies/entry points
localforge scan
localforge setup       # plain-prompt version: Ollama + API key, then the frontier model picks models to pull
localforge doctor      # checks Ollama installed/running + frontier API key set + hardware fit; also prints /scan's hardware detail
localforge models      # best-fit local model per modality for this machine
localforge catalog     # full model catalog, regardless of fit
localforge run "<task>" [--model gpt-5] [--usage] [--yes]   # one task in the current folder; --yes skips approval prompts
localforge clear / compact / auto / model / memory / scratch / summary / queue / stop / tell <note> / stream [on|off] / why   # session commands
localforge usage       # last-task + session token usage (meant for /usage inside the session)
localforge installed   # models actually on disk via Ollama, with sizes/total
localforge delete [MODEL...] [--yes]   # queue -> review -> confirm -> delete
localforge upgrade [--yes]  # swap installed models for better ones that fit, remove superseded ones localforge installed
localforge uninstall [--purge-ollama] [--yes]   # itemized removal, confirmed, then self-uninstalls
localforge help        # same as --help
localforge theme [matrix|dark|light]   # show/switch CLI color theme
localforge                             # bare, in a real terminal -> interactive session (see repl.py)
```

Requires [Ollama](https://ollama.com) running locally for actual model execution, and an API key for whichever frontier model is used (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, etc.). `localforge setup` handles both interactively and saves the key to `~/.config/localforge/config.env` (loaded automatically thereafter via `config.py`); `localforge doctor` checks all of this without changing anything. Running bare `localforge` (no subcommand) goes through the `invoke_without_command=True` callback in `cli.py`: in a real terminal (stdin *and* stdout both ttys) it opens the interactive session (`repl.py`); otherwise (pipe, script, CI) it prints the short getting-started panel and exits, so scripted callers never block on `input()`. That panel branches on whether a frontier model has been configured, so don't remove that check when touching the callback.

## Architecture

The pipeline is: **hardware detection → catalog matching → tool dispatch → orchestration loop**, each in its own module so a piece can change without touching the others.

- `cli_transport.py` — the second frontier transport: orchestrate via a provider's own logged-in CLI (`claude -p`, `codex exec`, `gemini -p`) instead of an API key, so usage draws on that account's subscription rather than per-token billing. It returns dataclasses (`CLIResponse`/`_Message`/`_ToolCall`) deliberately **shaped like LiteLLM's**, so `orchestrator.run()`'s loop — memory management, retries, usage stats — is byte-for-byte identical across both transports; only the call that produces a response differs. A headless CLI has no native tool-calling, so `_render_prompt()` asks for strict JSON and `_extract_json()` parses it back (tolerating code fences and surrounding prose, which models emit regardless of instructions); an unparseable reply degrades to "treat the text as the final answer" rather than failing the run. Per-provider commands live in `config.FRONTIER_CLI_AUTH`; flags/envelope shapes for all three were checked against each project's own published docs, and Anthropic is additionally verified live end to end; the others are still probed via `available()`/`logged_in()` at runtime, never assumed, so a wrong guess surfaces as "not installed" with install instructions. Two envelope shapes exist and both are handled: a single JSON object (claude, gemini) and a JSON Lines event stream (codex, where the reply is an `agent_message` item rather than a top-level key — parsing that as one object silently mangles it). Usage key names differ per CLI (`usage` vs Gemini's nested `stats`), so `_read_usage()` is deliberately tolerant and returns zeros for an unrecognised shape rather than inventing numbers. **Login is verified in `_prompt_for_auth_method()`, before the model menu** -- `available()` only checks that the binary is on PATH, so without the `logged_in()` probe setup would happily write a `cli_login` config that can't run. When the probe fails the user gets a recheck-or-fall-back-to-API-key choice, and "check again" re-probes in place rather than bouncing back to the auth menu. `run` catches `CLINotAvailableError` separately from the generic handler to add shell-level advice (`claude login`), since the CLI's own message says `/login` (its in-app slash command), which isn't what you type in a shell. `advisor.recommend_models(..., cli_provider=...)` must be routed the same way: under CLI login there is no API key, so a litellm call there would fail and silently degrade to the deterministic heuristic (this was a real bug). **Transport is detected by `isinstance(response, CLIResponse)`, never by probing for an attribute** — duck-typing misfires on mocks/proxies that auto-create attributes and silently mis-bills. Anything the CLI transport reports as cost is *notional* (what pay-per-token would have cost); `RunStats.frontier_via_subscription` marks it so the UI never presents subscription usage as separately-charged money.
- `banner.py` — the Matrix-style ASCII-art logo shown at the top of `localforge repl`. Baked in as a plain string (pyfiglet's "doom" font, generated once and pasted in — pyfiglet is **not** a runtime dependency) rather than an f-string, deliberately: `"doom"` was picked over the more common "ansi_shadow" figlet font specifically because it's 45 columns wide vs. 85 — verified via a real `pexpect` pty (default 80 columns) that the wider font silently falls back to plain text on an *ordinary* terminal, which defeats the point of having a banner. `render()` still has a one-line fallback (`▓▓▓ LOCALFORGE ▓▓▓`) for anything narrower than 45 columns (split panes, etc.). Every `console.print` here passes `highlight=False` — without it, Rich's automatic highlighter fragments the ASCII art's own slashes/parens into extra (same-color, so only visually harmless but ANSI-bloated) spans; confirmed by direct pty inspection, not just reasoning about it.
- `repl.py` — the interactive session started by `localforge` with no subcommand in a real terminal (see `cli.py`'s root callback: gated on `sys.stdin.isatty() and sys.stdout.isatty()`, so a pipe/script/CI invocation keeps the old print-and-exit `_print_getting_started()` behavior instead of hanging on `input()`). `run_repl(app, console)` dispatches every command by calling the *same* `typer.Typer` app in-process — `app(argv, standalone_mode=False)` — rather than re-implementing command logic, so a slash command can never drift out of sync with its `localforge <command>` CLI equivalent. Two things worth knowing if you touch this: (1) `typer.Exit` is a subclass of `Exception` (verified directly, not assumed), so it must be caught *before* the generic `except Exception` or every clean command exit gets misreported as an error — the loop already does this, keep the order. (2) A bare (non-slash) line is shorthand for `/run <the whole line>`, and that line is passed to `run` as **one** unsplit string (`_to_argv`), never `shlex.split` — a task description isn't shell syntax, and splitting it would mangle quotes/punctuation in the task text itself; only non-`run` commands get `shlex.split` for their args (model names, `--yes`, etc.). Any new `SLASH_HELP` line must avoid literal `[brackets]` for optional args (use `<angle brackets>` instead, matching `/run <task>`) — Rich's markup parser silently swallows unrecognized `[...]` spans, which is a real bug this project hit once (`/delete [names]` vanished from the printed help entirely). `tests/test_repl.py` guards both the bracket rule and the escape-code-count difference from `highlight=False`.
- `theme.py` — three `rich.theme.Theme` objects (`matrix`/`dark`/`light`) keyed by semantic style names (`success`, `error`, `warning`, `accent`, `panel.border`). `cli.py` uses these names everywhere (`[success]`, `[error]`, etc.) instead of literal color words like `[green]`/`[red]` — a literal color word bypasses Rich's theme system entirely, so if you add a new message, use a semantic name from this module, never a raw color. Applied via `console.push_theme(...)` in `_main`'s callback, *after* `config.load()` (not at `Console()` construction time, since the saved theme isn't in the environment yet at import time) — `push_theme` re-applies live, so `localforge theme <name>` can also call it directly to reflect the change in that same invocation. The `panel.border` key only takes effect because every `Panel(...)` call passes `border_style=` explicitly — Rich does *not* apply a theme to panel borders automatically, so a `Panel()` without it silently ignores the theme (this was a real bug once). `tests/test_edge_cases.py` asserts every `Panel()` call in `cli.py` sets a `border_style`; the destructive `uninstall` panel deliberately uses `border_style="error"` rather than `panel.border`, so it reads as alarming in every theme.
- `hardware.py` — detects OS/CPU/RAM/GPU/free disk space. GPU detection is NVIDIA via `nvidia-smi` first, falling back to Apple Silicon unified-memory heuristics (`arm64` + `Darwin`); no GPU means CPU-only. Free disk space is measured at `Path.home()` (where Ollama pulls actually land), via `shutil.disk_usage`.
- `catalog.py` + `catalog_data.yaml` — a static, hand-curated list of models tagged by `modality` (`coding`, `docs`, `general`; `judge`, resolved directly by `tools.Dispatcher.judge()` and never through the ordinary recommend/setup flow -- see **A dedicated judge model checks delegated output** below; plus reserved `image`/`video`), `runtime` (which backend serves it), hardware minimums, and `disk_gb` (approximate download size). `INTERNAL_MODALITIES` (currently `{"judge"}`) is subtracted from the modality set inside `recommendations()` (and mirrored in `advisor.recommend_models()`) -- get this wrong and `setup`'s plan-then-pull loop would list the judge model as something to download and then actually pull it, silently breaking "never downloaded automatically" for that feature; `localforge catalog` (the raw, unfiltered listing) still shows it, since that command is explicitly "every model regardless of fit." `candidates()` is a pure function returning every entry that fits the given `HardwareProfile` (see **Balanced model selection** below: memory while running, not just a RAM minimum); `best_match()` picks the balanced choice among them (`balanced_pick`: the highest `quality_tier` that still runs at `MIN_TOKENS_PER_SECOND`) — **unless** `installed` (the set of Ollama tags already on disk) is passed, in which case an already-installed *fitting* model wins over a higher-tier one that would need downloading. This is a fixed bug, not a nicety: re-running setup used to download `llama3.1:8b` (tier 1, 4.9 GB) while `mistral-nemo:12b` (tier 2, same modality) was already installed, because nothing in the pipeline ever looked at what was on disk. Two properties to preserve: (1) an installed model must still pass the hardware check — `installed` is intersected with `candidates()`, never used on its own, so a model that's on disk but too big for this machine is not picked; (2) among several installed fitting models the highest tier wins. `catalog.py` stays pure (no backend import): callers fetch the installed set via `OllamaBackend.list_installed()` and pass it in. `advisor.recommend_models(..., installed=...)` labels every candidate with `"installed": true/false` and tells the frontier model to strongly prefer installed ones — the advisor was the actual source of the reported download, since it had no way to know what was on disk — while still letting it deliberately choose an upgrade; its deterministic fallback (`_best_choice`) applies the same preference. `setup` prints a reuse-vs-download plan via `_print_model_plan()` *before* pulling anything, including a note when a higher-tier model also fits, so the upgrade trade-off is shown to the user rather than decided silently either way; it then only passes non-installed models to `ensure_available`. `tests/test_installed_preference.py` covers all of this, including the reporter's exact machine. This deterministic heuristic was chosen deliberately over a benchmark-driven approach (download-and-measure candidate models) for speed and predictability, and it's also the fallback `advisor.py` uses when the frontier-model-driven pick fails.
- `advisor.py` — `recommend_models(hardware, frontier_model, catalog=None)` lets the frontier model choose among `catalog.candidates()` per modality via a tool call whose JSON-schema parameters use an `enum` of only the fitting model names — this makes it structurally impossible for the frontier model to hallucinate a model outside the catalog. Any failure (network error, bad key, malformed/missing tool-call args) falls back to `catalog.best_match()` per modality; this fallback is unconditional and silent (no error surfaced to the user) by design, tested in `tests/test_advisor.py` since there's no real API key in tests. `setup` calls this *after* the API key step, not before, since the frontier model needs a key to be called at all.
- `backends/` — one module per serving runtime, behind the `Backend` protocol (`ensure_available`, `generate`) in `base.py`. `ollama.py` is implemented (REST calls to `localhost:11434`); `ensure_available` takes an optional `on_progress` callback invoked with each raw JSON event Ollama streams back from `/api/pull` (`{"status": ...}` or `{"status": "downloading", "total": N, "completed": N}`) — `cli.py`'s `setup` uses this to drive a real `rich.progress.Progress` bar (percentage/size/speed/ETA). Don't reintroduce the old drain-and-discard loop (`for _ in resp.iter_lines(): pass`) if touching this. `comfyui.py` is an intentional stub: image/video generation is job-based (submit → poll → fetch a file) rather than single-shot request/response like text, and returns `BackendResult(type="file", ...)` instead of `type="text"` — the orchestrator and tool layer already branch on this.
- `tools.py` — the `Dispatcher` class is the glue: given a tool name the frontier model called, it maps tool → modality → `catalog.best_match()` → backend, resolves the model once per modality per run (cached in `_resolved_models`), and runs it. It also resolves the judge model (`Dispatcher.judge()`, cached in `_judge_entry`) and calls it against delegated output (`_judge_check`/`_judge_check_async`) -- see **A dedicated judge model checks delegated output** below. `TASK_MODALITIES` is the single source of truth mapping a modality to its tool name/description; adding a new delegable modality means adding an entry here plus a backend, not touching the orchestrator loop. `build_tool_schemas(hardware, catalog)` **filters** to modalities that actually have a fitting model on this machine — it takes hardware for exactly this reason; exposing a tool the frontier model can only call to get a `NoFittingModelError` back wastes a round trip and confuses it. Don't drop those parameters back to a no-arg signature. `dispatch()` takes an optional `on_delegate(modality, ModelEntry)` callback invoked right before the backend call, so a caller can show the user which local model is actually handling a given subtask — this is how `cli.py`'s `run` prints `→ delegating coding to qwen2.5-coder:14b (local, via ollama)` per tool call; keep passing it through if you touch the dispatch path.

**Live activity + run-time model choice**: `tools.ActivityHooks` (on_frontier/on_delegate/on_token/on_done/on_pull) is how a run shows what's happening; `orchestrator.run(..., hooks=)` passes it to `Dispatcher`, and `cli._LiveActivity` renders it: a spinner only during frontier turns and while a local model loads, local output **streamed** indented under its "→ delegating" line, then a "✓ model finished: N tokens in Xs, R tok/s" line (rate measured from the first token, since wall time includes loading the model into memory). `OllamaBackend.generate(on_token=...)` switches to `stream: True`; without `on_token` it stays non-streaming. Before this, a run showed one spinner for minutes. `orchestrator.run()` also passes the Ollama installed set into `Dispatcher`/`build_tool_schemas`, so run time uses the same installed-first rule as setup. Without it the dispatcher silently pulled `qwen2.5-coder:14b` (9 GB) mid-run on a machine where setup had picked the installed 7b. Retries only switch to *installed* alternatives. `catalog._fits()` skips the free-disk check for installed models: right after that pull the Mac had 5.8 GB free and the installed 14b was being rejected for "not fitting". `tests/test_live_activity.py` covers all of this.

**Harness model (workspace.py, memory.py, `Conversation`)**: localforge works like Claude Code in the folder it's started in. The frontier model plans, investigates and reviews; local models write file contents. Tools are modeled on Claude Code's: `read_file` (Read), `list_files` (Glob), `search` (Grep), `edit_file` (Edit, small fix-ups only), `run_command` (Bash), `web_search`/`fetch_url`, and `update_todos` (TodoWrite). All are defined in `tools.DIRECT_TOOLS` with real JSON-schema parameters. `delegate_*_task(instructions, path?)` with a `path` makes the dispatcher send the local model the current file plus a "write the complete file" brief, extract the longest fenced block (`_extract_file_content`), and save it through `Workspace.write_file`. **The orchestrator deliberately has no `write_file`**: file content comes from local models (user's choice). Generated content is written straight to disk, so it doesn't need a round trip through the frontier transcript; only the diff summary comes back. Every write and command goes through the `Approver` (`cli._LiveActivity.approve`): a Claude-Code-style diff/command panel, then (y)es/(n)o/(a)lways-this-session. It auto-approves with `--yes` or `/auto on`, and **declines when stdin isn't a tty** so it never blocks. Write the prompt as `(y)es`, never `[y]es`, since Rich swallows `[y]` (seen live). `Workspace.resolve()` confines paths (`..` and symlinks included) to the project root, but that can't confine `run_command` (a shell can `cd` anywhere), so the approval prompt is the real control there. Don't describe it as a sandbox. **Conversation**: the session keeps one `Conversation` per folder (`cli._SessionState`, module-level because the REPL dispatches in-process); `run()` appends to it, and `messages[0]` is re-rendered each call from `SYSTEM_PROMPT` + a project snapshot + session memory. **Memory** (user's idea): once history passes `memory.COMPACT_AT_CHARS`, or on `/compact`, a local model (first fitting of general/docs/coding) folds all but the latest turn into a markdown memory note. The note goes into the system prompt and is saved in the project's `.localforge/` folder (see **Memory lives in the project**), so the next session in that folder resumes with it. `/clear` resets the conversation, and `--forget` also deletes the note. With no usable local model the oldest turns are dropped instead, so the cap always holds. That matters because under CLI login the whole history is flattened into one prompt every turn. **CLI prompt goes over stdin** for claude (`prompt_via_stdin`; 340k chars verified live), and argv for the others. Tool calls come back as `{"name", "arguments": {...}}`; a double-encoded string or the older flat `instructions` form is also accepted. `tests/test_harness.py` covers all of this.

**Local orchestrator (`local_transport.py`)**: a model id starting `ollama/` (or `ollama_chat/`) as the orchestrator always goes straight to Ollama's `/api/chat`, whatever auth settings are present. It uses the CLI transport's JSON decision protocol (`cli_transport._render_prompt` + `message_from_reply`) with `format: "json"` and `num_ctx` 16384, not native tool calling, because many open-weight models (Gemma) have no tool template in Ollama. Its responses are `CLIResponse(local=True)`, never counted as subscription or billed usage. **Reported bug this fixes:** choosing the local provider saved only the model, and `config.save()` merges, so a `cli_login` left from an earlier setup kept routing turns through `claude`, which failed on the Claude account's spend limit and then wrongly advised `claude login`. The rules now: setup and `/model` always write `AUTH_METHOD` + `PROVIDER` together (`AUTH_LOCAL`/`"local"` for Ollama); `cli._cli_provider_for()` never returns a CLI for a local model or an explicit `--model`; `config.save()` also updates `os.environ` so an in-session `/setup` or `/model` takes effect immediately; and `doctor` checks the local model is downloaded instead of probing `claude`. `cli_transport.probe()` keeps the CLI's own failure text, and `_cli_failure_advice()` tells a usage/spend limit (wait, or `/model`) apart from a sign-in problem (`claude login`). Setup's local menu comes from `local_transport.orchestrator_choices()` (installed models first, then catalog models that fit), not the old fixed 70B list nobody's laptop can run. **Small-model rails, all seen live with gemma3:4b:** an identical repeated tool call isn't re-run (`done_calls`); an answer that only promises work ("I will create…") with no tool call gets one nudge (`_PROMISE`); no installed model for a modality falls back to an installed model of another text modality (`TEXT_MODALITIES`); and any remaining download goes through the approver (`kind="download"`). The session label warns below `MIN_RELIABLE_BILLIONS` (7B). `tests/test_local_orchestrator.py` covers all of this. `tests/conftest.py` gives every test an empty config dir, restores `os.environ`, resets the module-level session, and pins setup's local menu; before it, tests read the developer's real `~/.config/localforge` and leaked `CONFIG_FILE` into each other.

**Streaming, trust, CRUD, scratchpad, memory, line editing** (all added together; each has its own test file):
- *Orchestrator streaming* (`answer_stream.py`, `tests/test_streaming.py`): the CLI-login and local transports return a JSON decision, so `AnswerStreamer` watches the partial text for `"final_answer": "` and decodes only that string, including escapes split across chunks (seen live: `\"` split between two deltas). A tool-call reply streams nothing, since its activity lines show instead. For claude, `stream_args` (`--output-format stream-json --verbose --include-partial-messages`, verified live) runs through `_run_streaming()` (Popen, prompt written from a thread, watchdog timeout); the final `result` event is re-serialized so envelope parsing is unchanged. Ollama uses `stream: true`, and the API-key path uses `litellm` `stream=True` + `stream_chunk_builder`. It's all fed by the `ActivityHooks.on_answer_text` hook. `cli._LiveActivity` renders it with `rich.live.Live(Markdown)`; every hook calls `_stop_spinner()` first, which also ends the live answer, and `reply_streamed` keeps `run` from printing the answer twice. Codex/gemini have no `stream_args`, so they fall back to printing the answer at the end.
- *Model choice reaches the CLI*: `FRONTIER_CLI_AUTH[...]["model_flag"]`; `claude -p` used to ignore the Opus/Sonnet/Haiku pick (verified live that `--model` changes the model actually used). `run --model claude-…` with a saved Claude login keeps the login (`_cli_provider_for`).
- *Session start* (`cli._start_session`, passed to `repl.run_repl(on_start=...)`): a folder-trust prompt (`trust.py`, remembered in `~/.config/localforge/trusted_folders.json`, subfolders included; "No" exits), then the orchestrator choice, both numbered with no default. With a usable orchestrator from last time (`_current_is_usable`: in `_model_choices()`, or a custom cloud id whose key/CLI exists) it's a short "1) Keep using it / 2) Choose a different model"; the full list appears only on 2, or when there's nothing usable to keep (e.g. a deleted local model, which is said explicitly). The user asked for this after resuming showed the whole list. A one-off `run` in an untrusted folder asks on a tty, and otherwise refuses unless `--yes`.
- *CRUD*: `make_dir`, `move_path` and `delete_path` join read/list/search/edit. Deletes are their own approval kind (`"delete"`), so "(a)lways allow file changes" never covers them. The project root can't be deleted, and a non-empty folder needs `recursive=true`, with the approval listing its files.
- *Scratchpad* (`scratchpad.py`, modeled on Claude Code's): per session, in the system temp dir (`localforge-<uid>/<folder>/<id>/scratchpad`, mode 700), reached as `scratchpad/…` through `Workspace.resolve()`. Changes inside it skip approval (`Workspace._allowed`). `move_path` from the scratchpad into the project is a promote: a normal create/update diff approval, after which the draft is removed. It's deleted at session end (`_save_memory_at_exit`) or after a one-off run. Nothing goes in the project, so there's nothing to `.gitignore`.
- *Memory* (`memory.py`, modeled on Claude Code's): `~/.config/localforge/projects/<folder>-<hash>/` holds `session.md` (the condensed last session) plus `memory/MEMORY.md` (the index) and one `<name>.md` per fact, with `name`/`description`/`type` frontmatter (`user|feedback|project|reference`). The orchestrator has `remember`/`forget` tools. At `/exit` the local keeper runs `extract_facts()` (JSON; an unusable reply changes nothing) and then `compact()` into session.md. Facts are re-read into the system prompt every `run()`. Memory never downloads a model, and an old single-file memory is migrated on load. `/memory` (`forget <name>`, `clear`) and `/scratch` (`clear`) are the user-facing commands.
- *Line editing* (`repl.LineReader`): on a tty the prompt is `prompt_toolkit`, with arrow keys, mid-line edits, Up/Down history (`~/.config/localforge/history`, mode 600), and a `/` menu (`SlashCompleter`, built from `SLASH_HELP` via `slash_commands()` so they can't drift) with Tab to complete. Plain `input()` printed `^[[D` for arrow keys on macOS and is now only the non-tty fallback. Ctrl+C clears the line; two presses in a row exit.
- *Tests*: `tests/conftest.py` also trusts the cwd (mark a test `untrusted` to opt out), puts scratchpads under pytest's temp dir, and drops the session scratchpad after each test.

**A local orchestrator's context window** (`local_transport.fit_to_context`, `tests/test_local_orchestrator.py`): Ollama silently drops whatever doesn't fit `num_ctx`, and the model then reads the spliced remains as if they were real. Reported with mistral-nemo:12b: "my read_file results are coming back corrupted… line 1535 spliced into the middle of a block at line 1276", after which it re-read the same files and refused to write anything. So localforge never hands Ollama a prompt that can't fit: `fit_to_context()` shortens the oldest tool results first, then drops the oldest turns (never the system message), then `_clamp()` cuts the middle of what's left — and the prompt says how many items were trimmed and to fetch them again. `num_ctx` is then sized to the prompt (`MIN_NUM_CTX` .. `max_context()`, `LOCALFORGE_LOCAL_CONTEXT` to raise the cap): too small corrupts, too large wastes the user's RAM. `CHARS_PER_TOKEN = 3` errs small on purpose, since code packs tighter than prose. Two matching guards: `Workspace(max_read_chars=...)` (cli passes `LOCAL_ORCHESTRATOR_READ_CHARS` = 12k when the orchestrator is local, so one read can't fill the window) and `memory.COMPACT_AT_CHARS_LOCAL` (20k, so history is condensed far sooner than the 60k a frontier model gets).

**Liveness** (`background.TaskRunner.toolbar`, `tests/test_background.py`; reported: "when nothing is happening, the user is confused"): the status line follows Claude Code's shape — `🔨 Forging with qwen2.5-coder:7b… (2m 14s · ↓ 3.1k tokens · writing app.py, 41 tok/s)`. One verb plus the model actually working right now (the user asked for that rather than different verbs), an animated hammer/anvil next to the braille spinner so it visibly ticks, rolling elapsed time, a running token count (`TaskState.tokens()`: local tokens exactly, the answer approximated), and "quiet for Ns" once a step has been silent for `QUIET_AFTER_SECONDS`. Emoji only when stdout is UTF-8 (`_unicode_ok`), ASCII otherwise. `runner.note_event()` is called from the hooks that mean progress. The foreground display's spinner uses the same wording.

**Usage limits pause a task instead of killing it** (`tests/test_usage_limits.py`; reported: "when localforge picks the paid model and the subscription or limit ends, it breaks"). `cli_transport.UsageLimitError` carries `provider` and `reset_at`, parsed from the provider's own message by `parse_reset_time()` ("your session limit resets 11:10pm (Europe/Lisbon)" → a local-time datetime, tomorrow if that time has passed; None when no time is given). `looks_like_limit()` keeps limits apart from sign-in failures, which must not be waited on. `orchestrator._as_usage_limit()` normalizes the three transports (typed error, LiteLLM `RateLimitError`, message text). In `_call_frontier` a limit never counts as transient: `hooks.on_limit` decides -- `"retry"` (after waiting), `("switch", model, provider)`, or None to raise. The orchestrator model/provider live in a mutable `orchestrator` dict so a switch continues the *same* turn with the conversation untouched: no work is lost and the user isn't asked again. `_LiveActivity.on_limit` waits with a countdown, watching `FRONTIER_MODEL_ENV_VAR` so `/model` (allowed while paused: `repl` exempts it from `BUSY_BLOCKED` when `runner.waiting`) switches and continues immediately. It refuses to wait when there's no reset time, when it's more than `MAX_LIMIT_WAIT_SECONDS` (6h) away, or after `MAX_LIMIT_WAITS` (3) waits in a row, and says the work is kept. `_BackgroundActivity` shows the countdown in the status bar and `/summary` ("Paused: …"), and `check_cancel` in `_limit_tick` makes `/stop` work while paused. Verified in a pty with a stand-in transport that raises a real limit error and then succeeds.

**Giving up on a limit used to lose the task's open-work note and its usage stats** (reported: resuming a task after a usage limit doesn't work). `orchestrator.run()` only called `_remember_if_unfinished()` (which saves to `open-work.json`, offered back at the next session's start -- see **A real feedback loop...** below) for `KeyboardInterrupt`/`OrchestrationError`; a `UsageLimitError` given up on (no reset time, too long a wait, or the user declining) is a `cli_transport.CLINotAvailableError`, which fell through uncaught -- nothing was saved, and `cli.py`'s handler for that exception type printed the error and exited without recording anything to `usage.json` either. Fixed: `CLINotAvailableError` now has an optional `stats` slot (mirroring `OrchestrationError`/`TaskCancelled`); `run()` catches it alongside `OrchestrationError`, attaches `stats` (no message trimming needed -- the raise happens before any tool_calls for the in-progress round are appended, so the conversation is already consistent, unlike the `KeyboardInterrupt` path), and calls `_remember_if_unfinished()` before re-raising; `cli.py`'s existing handler records the stats when present. `tests/test_usage_limits.py::test_giving_up_on_a_limit_still_saves_open_work_and_usage` covers this.

**The wait-and-resume path itself never engaged for a real Anthropic limit** (reported, with the exact live text: `claude exited 1: You've hit your session limit · resets 11:40am (America/Chicago)`; the previous fix above only made giving up graceful -- this is why it still had to be given up on in the first place). `cli_transport.looks_like_limit()` gates everything: `_as_usage_limit()` returns `None` (so `_call_frontier` never calls `hooks.on_limit` at all) unless it matches. `LIMIT_MARKERS` had specific phrases ("usage limit", "spend limit", "rate limit", ...) but not Anthropic's actual wording, "**session** limit" -- so the real message fell through as a plain `CLINotAvailableError`, which `_is_transient()` correctly refuses to retry (its own `_PERMANENT` list already has bare `"limit"`), so it raised immediately with no wait, matching the report exactly: control handed straight back, "I'd have to manually say resume." `parse_reset_time()` was never the problem -- verified it reads that exact message's reset time correctly; only `looks_like_limit()`'s gate was too narrow. This is also why the existing test (`SPEND_LIMIT` fixture) never caught it: that fixture's text happens to also contain a literal `"spend limit"` elsewhere in the same string, so it matched regardless of whether `"session limit"` itself was recognized -- a synthetic message that accidentally hid the gap a real one hit immediately. Fixed by adding a bare `"limit"` to `LIMIT_MARKERS` (matching `_is_transient`'s own `_PERMANENT` list, and `cli.py`'s separate advice-text `_LIMIT_MARKERS`, which already had it -- three lists, two of which already agreed). `cli.py`'s `_LIMIT_MARKERS` is now built from `cli_transport.LIMIT_MARKERS` directly instead of a hand-maintained duplicate, so the two can't drift apart the same way again. `tests/test_usage_limits.py` adds `SESSION_LIMIT` (the real message, deliberately with no other limit phrase in it) alongside `SPEND_LIMIT`, and covers both `_as_usage_limit()` and the full `on_limit()` wait with it.

**Background tasks with a live prompt** (`background.py`, `tests/test_background.py`; reported: streaming "takes over the terminal"): in an interactive REPL, `cli._main` creates a `TaskRunner` and passes it to `repl.run_repl(runner=...)`. Typed tasks go to `runner.submit()`, which starts the task on a worker thread or queues it. The worker runs the same `run` command (`_run_in_background` → `app(["run", task])`), and `_SessionState.make_activity()` gives the worker thread a `_BackgroundActivity` instead of `_LiveActivity`. **Terminal ownership:** while the runner exists, prompt_toolkit owns the terminal. The REPL loop runs under `patch_stdout(raw=True)`, so worker output lands above the prompt, and live status is the prompt's `bottom_toolbar` (`runner.toolbar`, `refresh_interval`). So `_BackgroundActivity` must never use Rich `Live`/`status` (two libraries moving the cursor garbles the screen), and local tokens only bump counters. **Approvals** hand off from the worker to the main thread (`runner.ask()` blocks on an Event; the prompt text becomes the question via `LineReader._message`; the REPL routes y/n/a to `runner.answer()`), since the worker must never read stdin. **Cancel** is cooperative: `/stop`, Ctrl+C with a task running, and `/exit` set `cancel_event`; hooks call `runner.check_cancel()`, which raises `KeyboardInterrupt` into the orchestrator's existing `TaskCancelled` trimming; `_run_streaming` kills `claude` if interrupted mid-answer. `/tell` notes are drained by the `poll_notes` hook at the top of each round. `repl.BUSY_BLOCKED` commands (`/clear`, `/compact`, `/model`, `/setup`, …) are refused while a task runs, because they mutate state the worker uses. `TaskRunner._running` is set and cleared under the lock with the queue check, and the first task's state is set up in `submit()` before the thread starts; both were real races (a stranded task, and a lost `/stop` or blank `/summary`). Non-tty paths and one-off `localforge run` stay synchronous, so the test suite never depends on threads for normal commands. Verified in a pty with a scripted stand-in orchestrator (which has to answer prompt_toolkit's cursor-position queries, or the toolbar never draws).

**`/memory clear`/`forget` and `/scratch clear` were a gap in that same rule** (reported: a slash command sometimes made the running task "completely stop"). Both mutate state a running task holds a live reference to -- `/memory clear` zeroes `_session.conversation.memory`/`.facts` on the same `Conversation` object the worker is reading, and `/scratch clear` `shutil.rmtree()`s the directory backing the running task's `Workspace` scratch root out from under it -- but neither was in `BUSY_BLOCKED`, unlike `/clear`/`/compact` which exist for exactly this reason. Compounding it, `TaskRunner._work()`'s `except BaseException: pass` gave zero visible output if either corrupted the task badly enough to raise -- a precise match for "the work completely stops" with no error. Fixed: `repl.MUTATING_SUBCOMMANDS = {"memory": {"clear", "forget"}, "scratch": {"clear"}}` blocks only those specific subactions while busy -- plain `/memory`/`/scratch` (read-only) still work, like `/usage` -- and `_work()` now prints an unexpected failure to stderr instead of swallowing it silently. `tests/test_background.py::test_the_repl_blocks_scratch_and_memory_mutations_while_busy_but_not_reads` covers the blocking half.

**A question typed while a task runs used to just queue behind it** (reported). `repl._looks_like_a_question()` is a cheap, deliberately imperfect heuristic (ends in "?", or opens with an interrogative word) -- getting it wrong only ever means a real question waits in the queue like before, never that a real task gets mistaken for a question. When it fires and `runner.busy`, `_read_eval` calls `runner.ask_side_question()` instead of `submit()`. `TaskRunner.ask_side_question()` (mirrors `ask_question()`, but there's no pending approval to piggyback on here) fires `side_question_handler` on its own daemon thread and returns immediately -- fire-and-forget, since the handler prints its own answer whenever it's ready. `cli._answer_side_question()` (wired to `runner.side_question_handler` alongside `question_handler`) answers from **only what's already cached** -- `_session.conversation.brief`/`.facts`/`.memory` -- never a fresh file read, so it's instant and the only extra local compute it costs is the one generation call itself; delegated to `memory.keeper()`'s resolved model, never the paid orchestrator. Silently does nothing (no panel printed) if there's no local model installed or the reply is empty -- a missed side question is never worth erroring over. `tests/test_repl.py` covers the heuristic, `tests/test_background.py` covers the repl wiring and `TaskRunner.ask_side_question()` itself, and `tests/test_clarify.py` covers `_answer_side_question()`'s cache-only grounding.

**Trimming the `/help` menu of near-duplicate read-only commands** (brainstormed, not reported): `/queue` and `/summary` both answered "what's waiting," and `/scan`/`/doctor` both touched hardware -- easy to end up typing the wrong one. Neither pair was collapsed by deleting a `cli.py` command (a slash command *is* the CLI command per `repl.py`'s dispatch above, so removing one would remove `localforge <command>` too); instead each redundant listing was folded into the other and the loser dropped from `SLASH_HELP`/`slash_commands()` only. `queue_command` (`cli.py`) no longer lists queued tasks itself -- `Dispatcher.summary()` already did (`background.py`'s `TaskRunner.summary()` appends the queue unconditionally, busy or not) -- so a bare `/queue` now just points at `/summary`, and `/queue clear` is the one thing it still does on its own. `doctor` gained a `_print_hardware(hw)` call (the same helper `scan` now delegates to) right after its own `detect_hardware()` call, so the one "is everything OK" command also answers "what's my hardware," and `/scan` came off the menu. `scan` the CLI command is untouched and still runs standalone (`localforge scan`, or even typed as `/scan` in a session -- `SLASH_HELP` only feeds completion and the printed list, dispatch itself calls the Typer app by name regardless). `tests/test_background.py::test_summary_queue_stop_tell_commands` and `tests/test_next_step_messaging.py::test_doctor_also_shows_the_detected_hardware` cover the two folds.

**Keeping the flow going when a step fails** (`tests/test_unblocking.py`): the repeat-call guard in `orchestrator._loop` caches **only successful** results (`done_calls`). Failures (an exception, or a text result `_failure_in()` recognizes: `[WARNING:`, `Error running`, `X failed:`, missing/bad arguments) count toward `MAX_ATTEMPTS_PER_CALL` (3) and are returned with a "why it failed / you can retry or unblock another way" note. Caching failures was the reported "flow stops" bug: a sane retry got "you already made this exact call… give your final answer". User declines are not failures. `Dispatcher._delegate` recovers from a raising first attempt via `_recover()` (another installed model, else the same model told the error) and raises one error naming both attempts only if that also fails. `DownloadDeclined` is never retried. `OllamaBackend._generate_streaming` has stuck-model guards: `num_predict` (`MAX_OUTPUT_TOKENS`), `_is_repeating()` loop detection (ignores low-variety tails such as divider lines), `MAX_GENERATION_SECONDS`, and a longer read timeout for model loading, each raising `LocalModelStuck` for recovery. `_call_frontier` retries a transient orchestrator failure once (`_is_transient`; never limits, sign-in, or missing tools). Ctrl+C during a task raises `TaskCancelled` after trimming that turn's half-finished steps (a dangling assistant tool call would make the next request invalid); the CLI prints "Stopped." and the session continues.

**Balanced model selection** (`catalog.py`, `tests/test_catalog_balance.py`; asked for: "the right balance, and keep system performance in mind"). The old "RAM ≥ min_ram_gb" rule gave the reporter's 16 GB M4 a 9 GB 14b coder *and* a 7 GB docs model, more than the machine has once their context caches are counted, so it swapped. Now:
- *Fit = memory while running.* `running_gb()` = download × `WEIGHTS_IN_MEMORY` + context cache (`kv_gb_per_8k`, worked out per model from its architecture in `catalog_data.yaml`) + `RUNTIME_OVERHEAD_GB`. It has to fit `ram_budget_gb()` (RAM less the larger of `SYSTEM_RESERVE_GB`/`SYSTEM_RESERVE_FRACTION`, kept for the OS and apps) and, on a GPU, `GPU_USABLE_FRACTION` of VRAM. Apple Silicon must satisfy both, since it's one pool (`_placement`). Image/video runtimes keep the plain minimums.
- *Each model gets its own context window.* `context_limit()` is the largest of `max_context()`, halved down to 8k, that still fits. A model fits only if it runs with at least 8k. The dispatcher passes it to `generate(context_limit=...)` and sizes prompts to it (`Dispatcher.prompt_chars`, `ollama.prompt_budget(limit)`, where `reply_room` keeps at most half the window for the reply), as do the memory keeper (`memory._room`) and a local orchestrator (`local_transport.context_window`, cached per model). `_retry_candidate` never switches to a model with a smaller window than the prompt was sized for. So mistral-nemo on a 16 GB Mac runs with 8k rather than being excluded or swapping at 32k.
- *Speed.* `tokens_per_second()` = memory bandwidth × `BANDWIDTH_EFFICIENCY` / active weights (`active_gb` for mixture-of-experts, which is why `qwen3-coder:30b` is fast on big machines). Bandwidth comes from `hardware.apple_bandwidth()` (Apple's published per-chip figures) or `TYPICAL_BANDWIDTH`. `balanced_pick` takes the best tier at or above `MIN_TOKENS_PER_SECOND` (15), and otherwise the fastest model.
- *One model when two won't fit.* `share_text_model()` (used by `recommendations()` and the advisor's fallback) uses the coding pick for docs/general when the two can't be resident together (`resident_capacity_gb`: unified memory on Apple, VRAM + spare RAM elsewhere). Models already installed are never swapped out. The advisor prompt shows each candidate's `running_gb` and `est_tokens_per_second` and asks for the same balance.
- *Catalog.* Sizes were checked against Ollama's registry (the manifest's layer sizes) on 2026-09-23. `kimi-k2` was removed (cloud-only, 0 bytes to download) and gemma3 is no longer tagged as a coder. "Thinking" models (qwen3, qwen3.5, gpt-oss) are left out on purpose, because their reasoning text could end up inside a generated file. Families whose architecture we couldn't pin down (gemma4, ministral-3) aren't listed yet. Results: 16 GB M4 → one `qwen2.5-coder:7b` (32k, ~19 tok/s); 8 GB M1 → `qwen2.5-coder:3b`; 48 GB M4 Pro → `qwen3-coder:30b` plus separate docs/general models.

**Local models grounded, checked and heard** (`tests/test_local_grounding.py`; asked for: "keep the open-weight models grounded and ensure they're doing their work properly and updating the orchestrator properly"). Before this, a local model saw a one-line preface and the orchestrator's instructions, nothing else, and nothing checked what it wrote.
- *Grounded:* `tools._prompt_for(modality, instructions, grounding)` sends a preface, `LOCAL_RULES` (match the project's conventions; use only APIs that exist in the given files, the standard library or declared dependencies, never invented ones; state assumptions in NOTES), then `brief.grounding_for_local()`, then the task last. The grounding is the brief's "How it's built", "Running and testing" and "Conventions and decisions" sections, or the opening of another tool's brief, capped at `GROUNDING_CHARS`, read once per task (`Dispatcher.grounding`). `Dispatcher.prompt_chars` subtracts this preamble, so the context-window budget still holds.
- *Checked:* before a delegated file reaches the user's approval, `verify.check()` parses it (Python `compile`, JSON, YAML, TOML, and `node --check` / `bash -n` when those tools are installed). A failure gets **one free local retry** with the exact error (shown as a `retry` activity line). If that also fails, nothing is written, the user isn't asked, and the orchestrator gets `delegate_*_task failed: ... doesn't parse`, which counts as a failure for the retry guard. A file type with no checker is written with no claim made about it. Parsing isn't correctness; tests and the orchestrator's review still cover that.
- *Heard:* the file directive asks for up to three `NOTES:` lines after the code block. `_split_notes()` takes them off, looking after the last fence so a README's own code blocks are safe, and never writes them into the file. The orchestrator's result carries the diff summary, `Syntax check: <language> parses.`, `The local model's notes: ...` (left out when they're "none") and the preview.
- Verified live with qwen2.5-coder:7b and a stdlib-only/logging/type-hints `AGENTS.md`: it followed all three conventions, and the parse check and notes reached the result.

**Context-window failures reach the orchestrator** (`tests/test_context_errors.py`; reported: "if the context window is large for the lower-weighted models, it errors and doesn't tell the frontier or the orchestrator"). Two causes, both seen against Ollama 0.34:
- *Ollama silently caps `num_ctx` at the model's trained length.* It was asked for 262k, loaded 32k, and cut the prompt with no error. `OllamaBackend.trained_context()` reads `<arch>.context_length` from `/api/show`, once per model (`_trained_context`; failures aren't cached). It's a limit everywhere a window is sized: `_with_context`, `Dispatcher.context_limit` (together with catalog.context_limit and a shrunk window), and `local_transport.context_window`, where a local orchestrator used to get 32k regardless of the model. As a last guard, `_with_context` raises `LocalPromptTooLarge` rather than send a prompt that can't fit. Verified live: with `LOCALFORGE_LOCAL_CONTEXT=65536`, a 40k-token prompt to the 32k-trained qwen2.5-coder:7b was refused with that message.
- *Ollama's reason was thrown away.* `error_from(resp, model)` replaces `raise_for_status()` in both generate paths and both `/api/chat` paths. It keeps the body's `error`, and memory failures (`_MEMORY_MARKERS`, which includes mid-stream "CUDA error: out of memory") become `LocalModelOutOfMemory`.
- *Recovery:* `_delegate` doesn't blindly retry a memory or size error (the same prompt would fail the same way). `Dispatcher.dispatch` catches `LocalModelOutOfMemory` once: it halves the window, remembers that for `SHRUNK_WINDOW_SECONDS` (`_shrunk_windows`), and re-runs the whole step, so reference files are re-trimmed and the orchestrator is told. If that fails too, or the window can't get smaller, the error carries Ollama's reason plus "memory is short... tell the user". `orchestrator._loop` returns it as a counted failure (`delegate_*_task failed: ...`).

**A task ends when it's done** (`tests/test_task_completion.py`; reported: "if there is an issue the overall process stops, so I need some check/loop to ensure the task is completed; hopefully AGENTS.md captures it"). A final answer used to end the task whatever state it was in. Now `_loop` records what the task did (`_Progress.note`: file changes, which are results starting with `_CHANGED`; check runs, which are `run_command` matching `_CHECK_COMMAND` (a user decline counts, so it isn't asked again) or `read_file` of a changed file; and the latest `update_todos`). Before a final answer ends the task, `_completion_gaps()` looks for:
- plan items not completed;
- files changed since the last check, with the brief's check commands quoted (`brief.section(..., ("definition of done", "running and testing"))`);
- an answer that gives up (`_GAVE_UP`, asked once).

Anything missing goes back as a `COMPLETION_PREFIX` user message, at most `MAX_COMPLETION_CHECKS` (3) times, so it can't loop. `memory._turn_starts` skips that prefix. The brief's `PROMPT` now asks `/goals` for a `## Definition of done` section (the exact test/lint/build commands). It's in `GROUNDING_SECTIONS` too, so local models see it, and the system prompt tells the orchestrator about it. A transient orchestrator failure now gets `MAX_FRONTIER_ATTEMPTS` (3) tries, waiting 2s then 6s, instead of one retry.

**A real feedback loop between the frontier model and the local models** (`tests/test_feedback_loop.py`; reported: "is there no feedback between the frontier model and the local models?"). Four gaps, closed without a frontier round trip for any of them:
- *A failed check reaches the next delegation on its own.* `Dispatcher._last_check_failure`/`_check_failure_shown` track the most recent failing `run_command` that matches `CHECK_COMMAND` (moved from `orchestrator.py` into `tools.py` so both can use one regex; `orchestrator._CHECK_COMMAND` now just imports it). A passing check (or a user decline) clears it. The next `path`-writing delegation gets it appended once ("The project's checks failed after the last change -- fix this too: ..."), so the orchestrator doesn't have to paste the exact failure text back in, and it isn't lost to a summary.
- *Local models see remembered preferences too.* `memory.facts_for_local()` renders `feedback`/`user`/`project` facts (not `reference` pointers) as plain rules; `Dispatcher.preferences()` reads it once per task and `_prompt_for()` adds a "Remembered preferences and corrections" section to every delegated prompt. Before, a saved fact like "never use print()" only ever reached the orchestrator's own instructions.
- *Corrections are logged, and repeats become lasting rules.* `memory.note_correction()`/`recent_corrections()` keep a capped JSONL log (`corrections.jsonl` in the project's `.localforge/`) of what a local model got wrong: `_delegate_to_file` logs a `"syntax"` entry on a failed check (and `"syntax (still failing)"` if the one free retry doesn't fix it either). `extract_facts()`'s `EXTRACT_PROMPT` is given the recent log and told: when the same kind of correction shows up more than once, save it as a `feedback` memory phrased as a rule -- which then reaches every future delegation via `facts_for_local()`.
- *Unfinished work is saved, not left to a summary.* `memory.save_open_work()`/`open_work()`/`clear_open_work()` keep up to `MAX_OPEN_WORK` (5) entries in `open-work.json`: the task string, why it stopped, its open plan items and its unchecked files. `Conversation.last_progress` holds the `_Progress` object `_loop` was building (survives the exception since it's on `conversation`, not a local var), so `run()`'s `except KeyboardInterrupt` / `except OrchestrationError` paths (`_remember_if_unfinished`) can compute the same two things `_completion_gaps()` looks for (`_open_items_and_unchecked`) even though there's no final answer to check. A task that finishes normally clears its own entry (`else:` branch of `run()`'s try). `cli._offer_open_work_at_start()` (after the brief-update offer) shows the most recent entry and asks: continue now (re-runs with `memory.RESUME_PREFIX` + the task + `describe_open_work()`), not now (asked again next session), or discard.

**Keeping the orchestrator to its job** (`tests/test_frontier_share.py`; reported: "the work is mostly done by the frontier model and not the open-weight models"). The core idea, in the user's words: the frontier model plans, delegates, validates and reconciles, the open-weight models execute, and quality stays as good as a frontier-only harness. `SYSTEM_PROMPT` states those four jobs. Measured live through `claude -p` on one ordinary step (Haiku, "add hello.py"):
- *The user's own Claude Code settings applied.* `claude -p` loaded `~/.claude/settings.json`, and there `advisorModel: opus` meant ordinary steps went on to Opus. In one measured step Opus was 75% of the cost, 1 run in 3 still hit Opus with `--disallowed-tools advisor` alone, and none of it was visible in `usage`. `isolation_args` now add `--setting-sources project` (the temp cwd holds no settings) plus `--disallowed-tools advisor`. - *Long tasks carry on by themselves* (reported with a screenshot: "did not converge within 40 rounds", then a manual "continue"). **Bad-local-output handling** (important gotcha if you touch `dispatch()`): `resolve()` already calls `catalog.best_match()`, which always returns the *highest quality_tier* fitting model up front — so on a machine where only one model fits a modality, there is nothing to "escalate to." `_looks_suspect(content, instructions)` is a cheap heuristic tripwire (empty output, a refusal phrase, or absurdly short relative to the instructions) checked after every `generate()` call; it is not a correctness checker (can't tell if code actually runs). On a flag, `dispatch()` retries exactly once via `_retry_candidate()`: a *different* fitting model if `catalog.candidates()` has one (regardless of tier direction, since there's usually nothing higher), otherwise the *same* model with `_reinforced_instructions()` appended (which explicitly tells the model its previous attempt was rejected and why). Both attempts go through `_run()`, which is the only place `local_tokens_generated` is incremented and `on_delegate` is called — this is deliberate: a retry still costs real local compute and the user should see both delegation attempts, so never bypass `_run()` for a retry path. If the retry is also flagged, the result is returned prefixed with `[WARNING: ...]` rather than silently passed through; `orchestrator.py`'s system prompt explicitly tells the frontier model to treat `[WARNING: ...]`-prefixed results with extra scrutiny and re-delegate rather than accept them at face value — the dispatcher-level retry and the frontier-level system-prompt instruction are two independent layers, not redundant; keep both if you touch either.

**A dedicated judge model checks delegated output** (`tests/test_judge.py`; asked for: reduce the paid orchestrator's own scrutiny of delegated results by having a local model give it a real semantic verdict, layered on top of -- never instead of -- `_looks_suspect()` above). `Dispatcher.judge(exclude=None)` resolves `catalog`'s `modality="judge"` entry (`atla/selene-mini`, chosen after checking Ollama's registry: post-trained from Llama-3.1-8B specifically for evaluation, small enough to be cheap) if it's installed; **never triggers its own download** either way (see `catalog.INTERNAL_MODALITIES` above) -- an eval feature isn't worth a surprise multi-GB pull, so it's opt-in via a manual `ollama pull atla/selene-mini`. If it isn't installed, `judge()` falls back to a *different* already-installed text model (`TEXT_MODALITIES`, same reasoning as `resolve()`'s stand-in), explicitly excluding `exclude` -- the model that actually produced the output being judged, so a stand-in never grades its own homework, which is exactly the bias a dedicated judge model exists to avoid. On the common single-local-model machine (see **Balanced model selection** below: often just one model fits at all) there's nothing else to fall back to, so the check is skipped rather than run at a known disadvantage on every task; `judge()` returns `None` in that case. `_judge_check()` sends `JUDGE_PROMPT` (deliberately excluding `LOCAL_RULES`/grounding/preferences -- those are the writer's brief, not the judge's job) and parses a strict `{"pass": bool, "reason": str}` reply via `cli_transport._extract_json`; any failure (no judge available, a crash, an unparseable reply, `JUDGE_TIMEOUT_SECONDS` elapsed) returns `None` rather than raising, since an eval hiccup must never fail a task that was otherwise fine. A `pass: false` verdict gets the same `[WARNING: ...]` treatment `_looks_suspect()` uses, with the judge's own reason attached, and never blocks a write -- the user still sees the diff and decides.

**Getting the "exclude the writer" model name right was the real bug here, not a test artifact.** The first implementation passed `self.resolve(modality).name` as `exclude` -- but `resolve()` is cached to its *first*-choice pick for the whole run and doesn't change after `_recover()` switches to a different installed model on a crash (see **Keeping the flow going when a step fails** below). That excluded the model that never actually wrote anything and left the real writer free to grade itself. Fixed by tracking `self._last_delegate_model`, set unconditionally at the top of `_run()` -- the one place every attempt (first try, crash-retry, suspect-retry) goes through -- so by the time a caller reads it right after `_delegate()`/`_delegate_to_file()` returns, it names whichever model actually produced the content being judged. `tests/test_judge.py::test_exclude_tracks_whichever_model_actually_wrote_the_output_after_a_crash_retry` pins this down.

**Parallel with the syntax check, not blocking on top of it.** For a `path` delegation, `_judge_check_async()` starts the judge call on a thread right after the file content is extracted and returns a `join()` closure; `_delegate_to_file()` calls `verify.check()` (and its own retry) in the meantime and only joins the judge right before the report is assembled -- so the judge's latency overlaps with the syntax check's instead of stacking on top of it. If a syntax retry changes what's actually written, the first (now-stale) judge call is abandoned (it's a daemon thread; harmless) and a fresh one is started on the fixed content. `tests/test_judge.py::test_the_judge_call_overlaps_with_the_syntax_check` proves the overlap deterministically (a fake `verify.check()` unblocks a judge call that would otherwise hang), rather than asserting on wall-clock timing. For a plain (no `path`) delegation there's nothing else running to overlap with, so the judge call there is just sequential, added after `_looks_suspect()` passes.
- `orchestrator.py` — the actual plan→delegate→collect loop, built directly on `litellm.completion()` rather than a multi-agent framework (LangGraph/AutoGen/CrewAI were considered; rejected for v1 because the project's real complexity is in the catalog-matching/dispatch logic, not conversation/turn-taking, and those frameworks' native "agents talking to agents" abstraction doesn't fit job-based image/video subagents any better than a plain tool function does). The loop is intentionally simple and inspectable: send messages + tool schemas to the frontier model, execute whatever tool calls come back via `Dispatcher`, feed results back as `role: tool` messages, repeat until the frontier model stops calling tools or `MAX_ROUNDS` is hit. `run()`'s own `on_delegate` parameter is just forwarded straight into `dispatcher.dispatch()` — it has no orchestration-level logic of its own. The system prompt instructs the frontier model to distrust delegated results by default and re-delegate with clearer instructions rather than pass through anything empty, refused, too short, or `[WARNING: ...]`-tagged — this is the frontier-side half of the bad-output handling (see `tools.py`'s `_looks_suspect`/retry logic for the dispatcher-side half); don't remove this instruction when editing the prompt, it's load-bearing for that feature. Non-convergence raises `OrchestrationError`, **not** a bare `RuntimeError` — it carries the `RunStats` accumulated up to that point, because a run that burns all `MAX_ROUNDS` still spent real frontier tokens/cost and local compute, and throwing that away leaves the user with no idea what a failed run cost. `cli.py`'s `run` catches it specifically (before the generic `except Exception`) and still records the stats in `_session_usage` (and prints them with `--usage`) before exiting non-zero; keep both the stats-carrying exception and that catch ordering if you touch either.

**Memory management**: deliberately minimal, by design (see project discussion if revisiting). Each `run()` call is fully stateless across invocations — no persistence, no cross-run project memory. *Within* one run, `KEEP_RECENT_TOOL_RESULTS` (4) bounds how many tool-result messages are kept in full; `_collapse_old_tool_results()` replaces older ones' `content` in place with a short `"[superseded: ...]"` placeholder (keeping the result's first line, so how each step went isn't lost) once that threshold is exceeded, tracked via a `tool_message_indices` list built up as tool messages are appended (call it once per round, after all of that round's tool calls have been appended — not per call, since a round can contain multiple tool calls). This is a plain truncation strategy, not summarization — no extra LLM call, and the assistant's own `tool_calls` messages (i.e. that it made the call) are never touched, only old result *content*. `_collapse_old_tool_results` is idempotent (checks for the `"[superseded:"` prefix before re-wrapping) since it runs every round against the same growing index list. If this ever needs to become genuine summarization or cross-run memory, that's new scope, not an extension of this mechanism.

**Usage metrics**: `run()` returns a `RunResult` (`answer: str`, `stats: RunStats`), not a bare string — `RunStats` tracks `frontier_prompt_tokens`/`frontier_completion_tokens` (from each LiteLLM response's `.usage`, accumulated in `_record_frontier_usage()` after every `completion()` call, including intermediate tool-calling rounds, not just the final one), `frontier_cost_usd` (via `litellm.completion_cost(completion_response=response)`, wrapped in a bare `except Exception` since an unpriced/unknown model shouldn't fail the run over a nice-to-have metric), and `local_tokens_generated` (copied from `dispatcher.local_tokens_generated` right before returning — `Dispatcher` accumulates this itself in `dispatch()` from each `BackendResult["tokens"]`, which `backends/ollama.py` populates from Ollama's own `eval_count` field in its `/api/generate` response; `backends/base.py`'s `BackendResult` TypedDict requires this key now, default `0` for backends that don't have a token count, e.g. a future image/video backend). **Usage is shown on request only** (user preference: no panel after every task). `run` appends `(frontier_model, stats)` to the process-level `cli._session_usage` list and prints the panel only with `--usage`; the `usage` command (reached as `/usage` in the REPL, which dispatches in-process, so the list is the session's history) shows the last task plus, from two tasks on, session totals via `_print_session_usage_panel()`, which keeps API-billed and subscription (notional) cost separate because tasks can mix transports. Keep both `result.answer` and `result.stats` in sync if you change `run()`'s return shape; every call site (`cli.py`, tests) unpacks it this way now, not as a bare string. `cli.py`'s `_usage_bar(local_tokens, frontier_tokens, width=40)` renders the Claude-Code-style horizontal split bar (green `█` for local, yellow for frontier, proportional block counts that always sum to `width`) shown above the numeric detail lines; it guards the `total == 0` case explicitly (returns a dim empty bar + "no tokens used") rather than dividing by zero. Tested directly in `tests/test_cli_usage_bar.py` by parsing the `[green]...[/green]`/`[yellow]...[/yellow]` markup segments and counting characters — don't change the tag structure without updating that parsing.
- `cli.py` — Typer entry point (`localforge` console script defined in `pyproject.toml`). The `run` command wraps the orchestrator call in a try/except to print a clean error instead of a raw traceback (LiteLLM raises rich exception types like `AuthenticationError` for missing API keys — surface `exc` directly, that's already a good user-facing message). `run`'s `--model` option defaults to `None` and is resolved inside the function body (`frontier_model or os.environ.get(config.FRONTIER_MODEL_ENV_VAR) or "claude-opus-5"`) rather than as the Typer default, since a static default is fixed at decorator/import time and can't see what `config.load()` puts into the environment at call time. `doctor` is the first-run diagnostic — it now also prints the detected `HardwareProfile` via the shared `_print_hardware()` helper (also used by the still-separate `scan` command), so the interactive `/help` menu only advertises `/doctor` and drops `/scan` from the list -- one command answers both "am I set up" and "what have I got" instead of two. `scan` itself is unchanged and still callable (`localforge scan`, or typed as `/scan` even though it's off the menu, since `repl.py` dispatches by calling the Typer app directly and never checks `SLASH_HELP` — that list only drives completion/`/help` text). It then always asks *which model within that provider* too, via `_prompt_for_model()` — a numbered list from `FRONTIER_MODEL_CHOICES[provider]` plus an "Other" free-text escape hatch (typing the number, the exact model id, or picking "Other" all work). The Anthropic list in `FRONTIER_MODEL_CHOICES` is a verified full lineup (Opus/Sonnet/Haiku/Fable); OpenAI/Gemini intentionally have only one curated entry each, since inventing a plausible-looking multi-entry lineup for providers we don't have verified current model ids for risks the user picking something that doesn't exist — extend those lists only with model ids you're confident are real and current, otherwise rely on "Other". If a key for the chosen provider already exists, `setup` reuses it instead of re-prompting, but neither the provider nor the model choice is ever skipped. Step order: Ollama check → provider/model/API key → hardware scan → `advisor.recommend_models()` → pull. The pull loop catches and logs a failure per model (network error, disk fills mid-download, etc.) and continues to the next one, reporting a summary at the end instead of letting one bad pull crash the rest of setup — mirror this pattern (not a bare loop) if you touch it. `installed`/`delete` are separate from the catalog entirely: they call `OllamaBackend.list_installed()`/`.delete()` (thin wrappers over Ollama's `/api/tags` and `DELETE /api/delete`) to show/remove what's actually on disk. `delete` builds a queue (from explicit args, or an interactive numbered/comma-separated/`all` prompt), shows the total space it will free, and requires one confirmation (skippable with `--yes`) before deleting anything — deletions run in a loop that catches per-model failures so one bad delete doesn't abort the rest of the queue, same pattern as the pull loop. `uninstall` is the most destructive command in the CLI (deletes all installed models, removes `~/.config/localforge`, optionally uninstalls Ollama itself + wipes `~/.ollama`, and finally shells out to `uv tool uninstall localforge` to remove itself) — it always prints an itemized `Panel` of exactly what will be removed before touching anything, and deliberately keeps the Ollama-app-itself removal (`--purge-ollama`) behind its own separate confirmation even when `--yes` is passed for the main prompt, since Ollama might be used by other tools the user has — don't collapse these into one blanket confirmation if you touch this. `help` is a plain alias command that reuses Click's own help text (`ctx.parent.get_help()`, where `ctx: typer.Context` must be a declared parameter — `click.get_current_context()` raises `RuntimeError: There is no active click context` when called this way inside a Typer command body). `theme_command` (registered as `theme`, named to avoid shadowing the imported `theme` module) shows/sets the active theme, persisting via `config.THEME_ENV_VAR`.

**`FRONTIER_PROVIDERS["local"]` (open-weight model as the orchestrator itself)**: `FRONTIER_PROVIDERS[provider]` being `None` now means two different things depending on *how* you got there — don't conflate them. `provider not in FRONTIER_PROVIDERS` means the user typed something invalid; `FRONTIER_PROVIDERS[provider] is None` (only true for `"local"`) means a *valid* provider that needs no API key at all. `setup` checks membership first, then branches on the env_var being `None` — this exact bug (treating `None` as "unknown provider" for a provider that validly needs no key) was introduced and fixed once already when `"local"` was added; don't reintroduce it if you touch this logic. Model ids for `"local"` use LiteLLM's `ollama/<model>` convention; `setup` strips the `ollama/` prefix and pulls that model via `OllamaBackend.ensure_available()` just like a delegated model, with the same per-failure-doesn't-abort handling as the main pull loop. `doctor`'s "configured" check treats `chosen_model.startswith("ollama/")` as sufficient on its own (no API key required) rather than requiring `found_keys` — don't require both.

**Google AI Studio** (`tests/test_google_ai_studio.py`; reported: "we can't use Google AI Studio"): LiteLLM routes a bare `gemini-2.5-pro` to **Vertex AI** (Google Cloud credentials), so the old saved id could never work with an AI Studio key. Gemini ids are `gemini/<model>` everywhere: `FRONTIER_MODEL_CHOICES`, `config.litellm_model_id()` (applied in `config.load()` to migrate a saved bare id, in `run`, and to `/model <id>`), and `cli_transport` strips the `gemini/` prefix for the `gemini` CLI's `--model`. `GOOGLE_API_KEY` is accepted as the key (`GEMINI_KEY_ALIASES`, copied to `GEMINI_API_KEY` on load). With a key, `_provider_models("gemini")` lists the key's own text models from Google's `/v1beta/models` (key in the `x-goog-api-key` header, never the URL; TTS/image/embedding/live filtered out; newest and pro first), cached per key only on success, and falls back to the curated list. That's how the menu stays current without us inventing Gemini model ids.

**`config.FRONTIER_CONSOLE_URLS`**: a plain UX convenience, not real authentication -- none of Anthropic/OpenAI/Gemini expose a public OAuth/browser-login flow for third-party tools (Claude Code's own browser login uses Anthropic's private first-party client credentials, not something to reverse-engineer or replicate here). When `setup` is about to prompt for an API key and none is found, it opens `FRONTIER_CONSOLE_URLS[provider]` via `webbrowser.open()` first; the user still pastes the key themselves. Neither `"local"` nor a provider with an already-set key ever triggers this.
