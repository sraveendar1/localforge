# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

`localforge` is a hardware-aware orchestration tool: it profiles the user's machine, matches that hardware against a curated catalog of open-weight models, pulls/serves the best-fitting ones locally via Ollama, and lets a frontier model of the user's choice (Claude, GPT, or any LiteLLM-supported provider) act as the orchestrator — planning a task and delegating subtasks (coding, docs, and reserved future modalities like image/video generation) to those local models. The design goal is **no vendor lock-in on the frontier model side**, and cost/hardware efficiency by keeping the actual grunt work local.

## Commands

Packaged and dependency-managed with [uv](https://docs.astral.sh/uv/) (`uv.lock` is committed; `.python-version` pins 3.12 — uv fetches that Python automatically if it's not present, so a pre-installed Python is not required).

```bash
# Setup for development
uv sync --extra dev

# Run tests
uv run pytest -q
uv run pytest tests/test_catalog.py -q          # single file
uv run pytest tests/test_catalog.py::test_best_match_picks_highest_tier_that_fits -q  # single test

# CLI during development
uv run localforge scan
uv run localforge doctor    # checks Ollama + frontier API key + hardware fit

# Install as a standalone end-user tool (no venv activation needed afterward)
./install.sh                 # shows what it will install + waits for Enter, then bootstraps Homebrew (macOS)+uv, installs the tool, runs setup
uv tool install --reinstall . # re-run manually after changing dependencies/entry points
localforge scan
localforge wizard      # same setup flow as a Textual terminal UI (screens, checkboxes, live log)
localforge setup       # plain-prompt version: Ollama + API key, then the frontier model picks models to pull
localforge doctor      # checks Ollama installed/running + frontier API key set + hardware fit
localforge models      # best-fit local model per modality for this machine
localforge catalog     # full model catalog, regardless of fit
localforge run "<task>" [--model gpt-5] [--usage]   # run the orchestration loop; usage only printed with --usage
localforge usage       # last-task + session token usage (meant for /usage inside the session)
localforge installed   # models actually on disk via Ollama, with sizes/total
localforge delete [MODEL...] [--yes]   # queue -> review -> confirm -> delete
localforge uninstall [--purge-ollama] [--yes]   # itemized removal, confirmed, then self-uninstalls
localforge help        # same as --help
localforge theme [matrix|dark|light]   # show/switch CLI color theme
localforge                             # bare, in a real terminal -> interactive session (see repl.py)
```

Requires [Ollama](https://ollama.com) running locally for actual model execution, and an API key for whichever frontier model is used (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, etc.). `localforge setup` handles both interactively and saves the key to `~/.config/localforge/config.env` (loaded automatically thereafter via `config.py`); `localforge doctor` checks all of this without changing anything. Running bare `localforge` (no subcommand) goes through the `invoke_without_command=True` callback in `cli.py`: in a real terminal (stdin *and* stdout both ttys) it opens the interactive session (`repl.py`); otherwise (pipe, script, CI) it prints the short getting-started panel and exits, so scripted callers never block on `input()`. That panel branches on whether a frontier model has been configured, so don't remove that check when touching the callback.

## Architecture

The pipeline is: **hardware detection → catalog matching → tool dispatch → orchestration loop**, each in its own module so a piece can change without touching the others.

- `cli_transport.py` — the second frontier transport: orchestrate via a provider's own logged-in CLI (`claude -p`, `codex exec`, `gemini -p`) instead of an API key, so usage draws on that account's subscription rather than per-token billing. It returns dataclasses (`CLIResponse`/`_Message`/`_ToolCall`) deliberately **shaped like LiteLLM's**, so `orchestrator.run()`'s loop — memory management, retries, usage stats — is byte-for-byte identical across both transports; only the call that produces a response differs. A headless CLI has no native tool-calling, so `_render_prompt()` asks for strict JSON and `_extract_json()` parses it back (tolerating code fences and surrounding prose, which models emit regardless of instructions); an unparseable reply degrades to "treat the text as the final answer" rather than failing the run. Per-provider commands live in `config.FRONTIER_CLI_AUTH`; flags/envelope shapes for all three were checked against each project's own published docs, and Anthropic is additionally verified live end to end; the others are still probed via `available()`/`logged_in()` at runtime, never assumed, so a wrong guess surfaces as "not installed" with install instructions. Two envelope shapes exist and both are handled: a single JSON object (claude, gemini) and a JSON Lines event stream (codex, where the reply is an `agent_message` item rather than a top-level key — parsing that as one object silently mangles it). Usage key names differ per CLI (`usage` vs Gemini's nested `stats`), so `_read_usage()` is deliberately tolerant and returns zeros for an unrecognised shape rather than inventing numbers. **Login is verified in `_prompt_for_auth_method()`, before the model menu** -- `available()` only checks that the binary is on PATH, so without the `logged_in()` probe setup would happily write a `cli_login` config that can't run. When the probe fails the user gets a recheck-or-fall-back-to-API-key choice, and "check again" re-probes in place rather than bouncing back to the auth menu. `run` catches `CLINotAvailableError` separately from the generic handler to add shell-level advice (`claude login`), since the CLI's own message says `/login` (its in-app slash command), which isn't what you type in a shell. `advisor.recommend_models(..., cli_provider=...)` must be routed the same way: under CLI login there is no API key, so a litellm call there would fail and silently degrade to the deterministic heuristic (this was a real bug). **Transport is detected by `isinstance(response, CLIResponse)`, never by probing for an attribute** — duck-typing misfires on mocks/proxies that auto-create attributes and silently mis-bills. Anything the CLI transport reports as cost is *notional* (what pay-per-token would have cost); `RunStats.frontier_via_subscription` marks it so the UI never presents subscription usage as separately-charged money.
- `banner.py` — the Matrix-style ASCII-art logo shown at the top of `localforge repl`. Baked in as a plain string (pyfiglet's "doom" font, generated once and pasted in — pyfiglet is **not** a runtime dependency) rather than an f-string, deliberately: `"doom"` was picked over the more common "ansi_shadow" figlet font specifically because it's 45 columns wide vs. 85 — verified via a real `pexpect` pty (default 80 columns) that the wider font silently falls back to plain text on an *ordinary* terminal, which defeats the point of having a banner. `render()` still has a one-line fallback (`▓▓▓ LOCALFORGE ▓▓▓`) for anything narrower than 45 columns (split panes, etc.). Every `console.print` here passes `highlight=False` — without it, Rich's automatic highlighter fragments the ASCII art's own slashes/parens into extra (same-color, so only visually harmless but ANSI-bloated) spans; confirmed by direct pty inspection, not just reasoning about it.
- `repl.py` — the interactive session started by `localforge` with no subcommand in a real terminal (see `cli.py`'s root callback: gated on `sys.stdin.isatty() and sys.stdout.isatty()`, so a pipe/script/CI invocation keeps the old print-and-exit `_print_getting_started()` behavior instead of hanging on `input()`). `run_repl(app, console)` dispatches every command by calling the *same* `typer.Typer` app in-process — `app(argv, standalone_mode=False)` — rather than re-implementing command logic, so a slash command can never drift out of sync with its `localforge <command>` CLI equivalent. Two things worth knowing if you touch this: (1) `typer.Exit` is a subclass of `Exception` (verified directly, not assumed), so it must be caught *before* the generic `except Exception` or every clean command exit gets misreported as an error — the loop already does this, keep the order. (2) A bare (non-slash) line is shorthand for `/run <the whole line>`, and that line is passed to `run` as **one** unsplit string (`_to_argv`), never `shlex.split` — a task description isn't shell syntax, and splitting it would mangle quotes/punctuation in the task text itself; only non-`run` commands get `shlex.split` for their args (model names, `--yes`, etc.). Any new `SLASH_HELP` line must avoid literal `[brackets]` for optional args (use `<angle brackets>` instead, matching `/run <task>`) — Rich's markup parser silently swallows unrecognized `[...]` spans, which is a real bug this project hit once (`/delete [names]` vanished from the printed help entirely). `tests/test_repl.py` guards both the bracket rule and the escape-code-count difference from `highlight=False`.
- `theme.py` — three `rich.theme.Theme` objects (`matrix`/`dark`/`light`) keyed by semantic style names (`success`, `error`, `warning`, `accent`, `panel.border`). `cli.py` uses these names everywhere (`[success]`, `[error]`, etc.) instead of literal color words like `[green]`/`[red]` — a literal color word bypasses Rich's theme system entirely, so if you add a new message, use a semantic name from this module, never a raw color. Applied via `console.push_theme(...)` in `_main`'s callback, *after* `config.load()` (not at `Console()` construction time, since the saved theme isn't in the environment yet at import time) — `push_theme` re-applies live, so `localforge theme <name>` can also call it directly to reflect the change in that same invocation. The `panel.border` key only takes effect because every `Panel(...)` call passes `border_style=` explicitly — Rich does *not* apply a theme to panel borders automatically, so a `Panel()` without it silently ignores the theme (this was a real bug once). `tests/test_edge_cases.py` asserts every `Panel()` call in `cli.py` sets a `border_style`; the destructive `uninstall` panel deliberately uses `border_style="error"` rather than `panel.border`, so it reads as alarming in every theme.
- `hardware.py` — detects OS/CPU/RAM/GPU/free disk space. GPU detection is NVIDIA via `nvidia-smi` first, falling back to Apple Silicon unified-memory heuristics (`arm64` + `Darwin`); no GPU means CPU-only. Free disk space is measured at `Path.home()` (where Ollama pulls actually land), via `shutil.disk_usage`.
- `catalog.py` + `catalog_data.yaml` — a static, hand-curated list of models tagged by `modality` (`coding`, `docs`, `general`, plus reserved `image`/`video`), `runtime` (which backend serves it), hardware minimums, and `disk_gb` (approximate download size). `candidates()` is a pure function returning every entry whose RAM/VRAM/disk minimums are met by the given `HardwareProfile`; `best_match()` picks the highest `quality_tier` among them — **unless** `installed` (the set of Ollama tags already on disk) is passed, in which case an already-installed *fitting* model wins over a higher-tier one that would need downloading. This is a fixed bug, not a nicety: re-running setup used to download `llama3.1:8b` (tier 1, 4.9 GB) while `mistral-nemo:12b` (tier 2, same modality) was already installed, because nothing in the pipeline ever looked at what was on disk. Two properties to preserve: (1) an installed model must still pass the hardware check — `installed` is intersected with `candidates()`, never used on its own, so a model that's on disk but too big for this machine is not picked; (2) among several installed fitting models the highest tier wins. `catalog.py` stays pure (no backend import): callers fetch the installed set via `OllamaBackend.list_installed()` and pass it in. `advisor.recommend_models(..., installed=...)` labels every candidate with `"installed": true/false` and tells the frontier model to strongly prefer installed ones — the advisor was the actual source of the reported download, since it had no way to know what was on disk — while still letting it deliberately choose an upgrade; its deterministic fallback (`_best_choice`) applies the same preference. `setup` prints a reuse-vs-download plan via `_print_model_plan()` *before* pulling anything, including a note when a higher-tier model also fits, so the upgrade trade-off is shown to the user rather than decided silently either way; it then only passes non-installed models to `ensure_available`. `tests/test_installed_preference.py` covers all of this, including the reporter's exact machine. This deterministic heuristic was chosen deliberately over a benchmark-driven approach (download-and-measure candidate models) for speed and predictability, and it's also the fallback `advisor.py` uses when the frontier-model-driven pick fails.
- `advisor.py` — `recommend_models(hardware, frontier_model, catalog=None)` lets the frontier model choose among `catalog.candidates()` per modality via a tool call whose JSON-schema parameters use an `enum` of only the fitting model names — this makes it structurally impossible for the frontier model to hallucinate a model outside the catalog. Any failure (network error, bad key, malformed/missing tool-call args) falls back to `catalog.best_match()` per modality; this fallback is unconditional and silent (no error surfaced to the user) by design, tested in `tests/test_advisor.py` since there's no real API key in tests. `setup`/`wizard` call this *after* the API key step, not before, since the frontier model needs a key to be called at all.
- `backends/` — one module per serving runtime, behind the `Backend` protocol (`ensure_available`, `generate`) in `base.py`. `ollama.py` is implemented (REST calls to `localhost:11434`); `ensure_available` takes an optional `on_progress` callback invoked with each raw JSON event Ollama streams back from `/api/pull` (`{"status": ...}` or `{"status": "downloading", "total": N, "completed": N}`) — `cli.py`'s `setup` uses this to drive a real `rich.progress.Progress` bar (percentage/size/speed/ETA), `tui.py`'s `ModelsScreen` uses it to write throttled percentage lines to the `Log` widget (every ~10%, not every event — an unthrottled callback floods the log). Don't reintroduce the old drain-and-discard loop (`for _ in resp.iter_lines(): pass`) if touching this. `comfyui.py` is an intentional stub: image/video generation is job-based (submit → poll → fetch a file) rather than single-shot request/response like text, and returns `BackendResult(type="file", ...)` instead of `type="text"` — the orchestrator and tool layer already branch on this.
- `tools.py` — the `Dispatcher` class is the glue: given a tool name the frontier model called, it maps tool → modality → `catalog.best_match()` → backend, resolves the model once per modality per run (cached in `_resolved_models`), and runs it. `TASK_MODALITIES` is the single source of truth mapping a modality to its tool name/description; adding a new delegable modality means adding an entry here plus a backend, not touching the orchestrator loop. `build_tool_schemas(hardware, catalog)` **filters** to modalities that actually have a fitting model on this machine — it takes hardware for exactly this reason; exposing a tool the frontier model can only call to get a `NoFittingModelError` back wastes a round trip and confuses it. Don't drop those parameters back to a no-arg signature. `dispatch()` takes an optional `on_delegate(modality, ModelEntry)` callback invoked right before the backend call, so a caller can show the user which local model is actually handling a given subtask — this is how `cli.py`'s `run` prints `→ delegating coding to qwen2.5-coder:14b (local, via ollama)` per tool call; keep passing it through if you touch the dispatch path.

**Bad-local-output handling** (important gotcha if you touch `dispatch()`): `resolve()` already calls `catalog.best_match()`, which always returns the *highest quality_tier* fitting model up front — so on a machine where only one model fits a modality, there is nothing to "escalate to." `_looks_suspect(content, instructions)` is a cheap heuristic tripwire (empty output, a refusal phrase, or absurdly short relative to the instructions) checked after every `generate()` call; it is not a correctness checker (can't tell if code actually runs). On a flag, `dispatch()` retries exactly once via `_retry_candidate()`: a *different* fitting model if `catalog.candidates()` has one (regardless of tier direction, since there's usually nothing higher), otherwise the *same* model with `_reinforced_instructions()` appended (which explicitly tells the model its previous attempt was rejected and why). Both attempts go through `_run()`, which is the only place `local_tokens_generated` is incremented and `on_delegate` is called — this is deliberate: a retry still costs real local compute and the user should see both delegation attempts, so never bypass `_run()` for a retry path. If the retry is also flagged, the result is returned prefixed with `[WARNING: ...]` rather than silently passed through; `orchestrator.py`'s system prompt explicitly tells the frontier model to treat `[WARNING: ...]`-prefixed results with extra scrutiny and re-delegate rather than accept them at face value — the dispatcher-level retry and the frontier-level system-prompt instruction are two independent layers, not redundant; keep both if you touch either.
- `orchestrator.py` — the actual plan→delegate→collect loop, built directly on `litellm.completion()` rather than a multi-agent framework (LangGraph/AutoGen/CrewAI were considered; rejected for v1 because the project's real complexity is in the catalog-matching/dispatch logic, not conversation/turn-taking, and those frameworks' native "agents talking to agents" abstraction doesn't fit job-based image/video subagents any better than a plain tool function does). The loop is intentionally simple and inspectable: send messages + tool schemas to the frontier model, execute whatever tool calls come back via `Dispatcher`, feed results back as `role: tool` messages, repeat until the frontier model stops calling tools or `MAX_ROUNDS` is hit. `run()`'s own `on_delegate` parameter is just forwarded straight into `dispatcher.dispatch()` — it has no orchestration-level logic of its own. The system prompt instructs the frontier model to distrust delegated results by default and re-delegate with clearer instructions rather than pass through anything empty, refused, too short, or `[WARNING: ...]`-tagged — this is the frontier-side half of the bad-output handling (see `tools.py`'s `_looks_suspect`/retry logic for the dispatcher-side half); don't remove this instruction when editing the prompt, it's load-bearing for that feature. Non-convergence raises `OrchestrationError`, **not** a bare `RuntimeError` — it carries the `RunStats` accumulated up to that point, because a run that burns all `MAX_ROUNDS` still spent real frontier tokens/cost and local compute, and throwing that away leaves the user with no idea what a failed run cost. `cli.py`'s `run` catches it specifically (before the generic `except Exception`) and still records the stats in `_session_usage` (and prints them with `--usage`) before exiting non-zero; keep both the stats-carrying exception and that catch ordering if you touch either.

**Memory management**: deliberately minimal, by design (see project discussion if revisiting). Each `run()` call is fully stateless across invocations — no persistence, no cross-run project memory. *Within* one run, `KEEP_RECENT_TOOL_RESULTS` (4) bounds how many tool-result messages are kept in full; `_collapse_old_tool_results()` replaces older ones' `content` in place with a short `"[superseded: ...]"` placeholder once that threshold is exceeded, tracked via a `tool_message_indices` list built up as tool messages are appended (call it once per round, after all of that round's tool calls have been appended — not per call, since a round can contain multiple tool calls). This is a plain truncation strategy, not summarization — no extra LLM call, and the assistant's own `tool_calls` messages (i.e. that it made the call) are never touched, only old result *content*. `_collapse_old_tool_results` is idempotent (checks for the `"[superseded:"` prefix before re-wrapping) since it runs every round against the same growing index list. If this ever needs to become genuine summarization or cross-run memory, that's new scope, not an extension of this mechanism.

**Usage metrics**: `run()` returns a `RunResult` (`answer: str`, `stats: RunStats`), not a bare string — `RunStats` tracks `frontier_prompt_tokens`/`frontier_completion_tokens` (from each LiteLLM response's `.usage`, accumulated in `_record_frontier_usage()` after every `completion()` call, including intermediate tool-calling rounds, not just the final one), `frontier_cost_usd` (via `litellm.completion_cost(completion_response=response)`, wrapped in a bare `except Exception` since an unpriced/unknown model shouldn't fail the run over a nice-to-have metric), and `local_tokens_generated` (copied from `dispatcher.local_tokens_generated` right before returning — `Dispatcher` accumulates this itself in `dispatch()` from each `BackendResult["tokens"]`, which `backends/ollama.py` populates from Ollama's own `eval_count` field in its `/api/generate` response; `backends/base.py`'s `BackendResult` TypedDict requires this key now, default `0` for backends that don't have a token count, e.g. a future image/video backend). **Usage is shown on request only** (user preference: no panel after every task). `run` appends `(frontier_model, stats)` to the process-level `cli._session_usage` list and prints the panel only with `--usage`; the `usage` command (reached as `/usage` in the REPL, which dispatches in-process, so the list is the session's history) shows the last task plus, from two tasks on, session totals via `_print_session_usage_panel()`, which keeps API-billed and subscription (notional) cost separate because tasks can mix transports. Keep both `result.answer` and `result.stats` in sync if you change `run()`'s return shape; every call site (`cli.py`, tests) unpacks it this way now, not as a bare string. `cli.py`'s `_usage_bar(local_tokens, frontier_tokens, width=40)` renders the Claude-Code-style horizontal split bar (green `█` for local, yellow for frontier, proportional block counts that always sum to `width`) shown above the numeric detail lines; it guards the `total == 0` case explicitly (returns a dim empty bar + "no tokens used") rather than dividing by zero. Tested directly in `tests/test_cli_usage_bar.py` by parsing the `[green]...[/green]`/`[yellow]...[/yellow]` markup segments and counting characters — don't change the tag structure without updating that parsing.
- `cli.py` — Typer entry point (`localforge` console script defined in `pyproject.toml`). The `run` command wraps the orchestrator call in a try/except to print a clean error instead of a raw traceback (LiteLLM raises rich exception types like `AuthenticationError` for missing API keys — surface `exc` directly, that's already a good user-facing message). `run`'s `--model` option defaults to `None` and is resolved inside the function body (`frontier_model or os.environ.get(config.FRONTIER_MODEL_ENV_VAR) or "claude-opus-5"`) rather than as the Typer default, since a static default is fixed at decorator/import time and can't see what `config.load()` puts into the environment at call time. `doctor` is the first-run diagnostic — it distinguishes "no key at all", "key(s) found but no `LOCALFORGE_FRONTIER_MODEL` chosen yet" (ambiguous — surfaced as a warning, not silently resolved), and "configured" — extend `FRONTIER_PROVIDERS`/`FRONTIER_API_KEY_ENV_VARS`/`FRONTIER_MODEL_CHOICES`/`FRONTIER_MODEL_ENV_VAR` in `config.py` when adding a new provider (both `cli.py` and `tui.py` import from there, don't redefine locally; `FRONTIER_DEFAULT_MODELS` is derived from `FRONTIER_MODEL_CHOICES[provider][0]`, don't set it independently). `setup` **always** asks which provider to use explicitly via `_prompt_for_provider()`, even if a key already exists in the environment — this is deliberate: don't reintroduce silently picking a provider from whichever key happens to be set, since a user could have multiple unrelated keys exported. **No selection prompt in `setup` may carry a `default=`.** This is a fixed bug, not a style preference: the provider prompt used to be `typer.prompt(..., default="anthropic")`, so a single stray/buffered Enter — e.g. the one pressed moments earlier at `install.sh`'s "Press Enter to continue" — was consumed by it and silently selected Anthropic, and the user never saw a choice. Both `_prompt_for_provider()` and `_prompt_for_model()` are now numbered menus that loop until a valid answer, re-asking on empty/invalid input, and both call `_drain_buffered_input()` (a `termios.tcflush` no-op when stdin isn't a tty) first to discard keystrokes typed before the prompt appeared. `tests/test_setup_prompts.py` guards all of this. It then always asks *which model within that provider* too, via `_prompt_for_model()` — a numbered list from `FRONTIER_MODEL_CHOICES[provider]` plus an "Other" free-text escape hatch (typing the number, the exact model id, or picking "Other" all work). The Anthropic list in `FRONTIER_MODEL_CHOICES` is a verified full lineup (Opus/Sonnet/Haiku/Fable); OpenAI/Gemini intentionally have only one curated entry each, since inventing a plausible-looking multi-entry lineup for providers we don't have verified current model ids for risks the user picking something that doesn't exist — extend those lists only with model ids you're confident are real and current, otherwise rely on "Other". If a key for the chosen provider already exists, `setup` reuses it instead of re-prompting, but neither the provider nor the model choice is ever skipped. Step order: Ollama check → provider/model/API key → hardware scan → `advisor.recommend_models()` → pull. The pull loop catches and logs a failure per model (network error, disk fills mid-download, etc.) and continues to the next one, reporting a summary at the end instead of letting one bad pull crash the rest of setup — mirror this pattern (not a bare loop) if you touch it. `installed`/`delete` are separate from the catalog entirely: they call `OllamaBackend.list_installed()`/`.delete()` (thin wrappers over Ollama's `/api/tags` and `DELETE /api/delete`) to show/remove what's actually on disk. `delete` builds a queue (from explicit args, or an interactive numbered/comma-separated/`all` prompt), shows the total space it will free, and requires one confirmation (skippable with `--yes`) before deleting anything — deletions run in a loop that catches per-model failures so one bad delete doesn't abort the rest of the queue, same pattern as the pull loop. `uninstall` is the most destructive command in the CLI (deletes all installed models, removes `~/.config/localforge`, optionally uninstalls Ollama itself + wipes `~/.ollama`, and finally shells out to `uv tool uninstall localforge` to remove itself) — it always prints an itemized `Panel` of exactly what will be removed before touching anything, and deliberately keeps the Ollama-app-itself removal (`--purge-ollama`) behind its own separate confirmation even when `--yes` is passed for the main prompt, since Ollama might be used by other tools the user has — don't collapse these into one blanket confirmation if you touch this. `help` is a plain alias command that reuses Click's own help text (`ctx.parent.get_help()`, where `ctx: typer.Context` must be a declared parameter — `click.get_current_context()` raises `RuntimeError: There is no active click context` when called this way inside a Typer command body). `theme_command` (registered as `theme`, named to avoid shadowing the imported `theme` module) shows/sets the active theme, persisting via `config.THEME_ENV_VAR`.

**`FRONTIER_PROVIDERS["local"]` (open-weight model as the orchestrator itself)**: `FRONTIER_PROVIDERS[provider]` being `None` now means two different things depending on *how* you got there — don't conflate them. `provider not in FRONTIER_PROVIDERS` means the user typed something invalid; `FRONTIER_PROVIDERS[provider] is None` (only true for `"local"`) means a *valid* provider that needs no API key at all. `setup`/`tui.py`'s `ApiKeyScreen` both check membership first, then branch on the env_var being `None` — this exact bug (treating `None` as "unknown provider" for a provider that validly needs no key) was introduced and fixed once already when `"local"` was added; don't reintroduce it if you touch this logic. Model ids for `"local"` use LiteLLM's `ollama/<model>` convention; `setup` strips the `ollama/` prefix and pulls that model via `OllamaBackend.ensure_available()` just like a delegated model, with the same per-failure-doesn't-abort handling as the main pull loop. `doctor`'s "configured" check treats `chosen_model.startswith("ollama/")` as sufficient on its own (no API key required) rather than requiring `found_keys` — don't require both.

**`config.FRONTIER_CONSOLE_URLS`**: a plain UX convenience, not real authentication -- none of Anthropic/OpenAI/Gemini expose a public OAuth/browser-login flow for third-party tools (Claude Code's own browser login uses Anthropic's private first-party client credentials, not something to reverse-engineer or replicate here). When `setup` is about to prompt for an API key and none is found, it opens `FRONTIER_CONSOLE_URLS[provider]` via `webbrowser.open()` first; the user still pastes the key themselves. `tui.py`'s `ApiKeyScreen` does the same in `on_radio_set_changed`, but guards against reopening the same provider's tab every time the user toggles between radio buttons while deciding, via a per-screen-instance `self._opened_console_for: set[str]` — don't remove that guard, or switching back and forth between providers will spam new browser tabs. Neither `"local"` nor a provider with an already-set key ever triggers this.
- `tui.py` — the `localforge wizard` Textual UI, same step order/principle as `setup`: `WelcomeScreen` → `OllamaScreen` (backgrounds the install/running check via `@work(thread=True)`, updates widgets through `self.app.call_from_thread` since Textual widgets aren't thread-safe to touch directly from a worker) → `ApiKeyScreen` (`RadioSet` for provider + a `Select` for model, populated per-provider from `config.FRONTIER_MODEL_CHOICES` by `_populate_models()`, with a `self.OTHER` sentinel value that reveals a free-text `Input` for a custom model id + masked `Input` for the API key; **always shown**, never skipped based on environment state — `on_radio_set_changed` re-populates the model `Select` for the newly picked provider, hides the API key `Input` entirely for `"local"` (`env_var is None`), and otherwise shows a "leave empty to reuse" hint when that provider's key is already set; `on_button_pressed` branches on `env_var is None` first before touching `os.environ.get(env_var)` — passing `None` to that crashes. `on_radio_set_changed` also **clears** the API key `Input` on every provider switch: the field is masked, so a key typed for one provider that survives a switch would be invisibly saved under the *new* provider's env var on Save (a real bug once — `tests/test_edge_cases.py` guards it). Note: unlike `setup`, the wizard does not currently pull the orchestrator model itself for the `"local"` provider (only `ModelsScreen`'s delegated models get pulled) — that's a known gap, not a design choice; use `localforge setup` or pre-pull manually if picking `"local"` via the wizard.) → `ModelsScreen(frontier_model)` (backgrounds `advisor.recommend_models()`, then shows checkboxes + a `Log` widget streaming pull progress) → `DoneScreen`. Widget `id`s can't contain `:` or `.` (Textual's `check_identifiers` rejects them), which model names like `qwen2.5-coder:14b` do — see `_safe_id()` for the sanitizing helper; don't build widget ids directly from model/provider names elsewhere without it. Tested headlessly via Textual's `App.run_test(size=(120, 60))` pilot (a small default virtual terminal makes off-screen widgets fail `pilot.click()` with `OutOfBounds` — size up if that happens) rather than a real terminal; when testing config-saving flows this way, always set `LOCALFORGE_CONFIG_DIR` to a temp dir first so it doesn't write into the real user's `~/.config/localforge/`.

### Extending to a new modality (e.g. real image generation)

1. Implement `backends/comfyui.py`'s `ensure_available`/`generate` (or add a new backend module) and register it in `backends/__init__.py`'s `BACKENDS` dict.
2. Add catalog entries in `catalog_data.yaml` with the right `modality`/`runtime`/hardware minimums.
3. Add a `TASK_MODALITIES` entry in `tools.py`.

Nothing in `orchestrator.py` needs to change — this is the intended seam.

### `install.sh` notes

It prints an itemized "this will install..." banner (Homebrew if missing, Ollama if missing, models, the CLI tool) and waits for Enter before doing anything, computed by checking `command -v brew`/`ollama` directly in bash — keep that check in sync if the underlying install logic in `cli.py`'s `setup` changes what it installs. The `read` for that pause is explicitly redirected from `/dev/tty`, not left on stdin: when the script runs as `curl ... | bash`, stdin is the script itself, so an unredirected `read` would misbehave (consume script content, or hit EOF) instead of prompting the user; the `< /dev/tty` redirect combined with `|| true` also means it falls through automatically (no hang) when there's no controlling terminal at all, e.g. a non-interactive CI context. **The `localforge setup` invocation needs the same treatment** and gets it (`setup < /dev/tty`, guarded by the `HAVE_TTY` probe with a plain-stdin fallback). `HAVE_TTY` really opens `/dev/tty` (`{ : < /dev/tty; } 2>/dev/null`) because `[ -e /dev/tty ]` is true in CI/containers where opening it fails. The child process inherits the script's stdin, so under `curl ... | bash` every interactive prompt inside `setup` would read the curl pipe, hit EOF, and abort. Any future interactive command invoked from this script needs the same redirect. **The opposite applies to the final bare `localforge` call:** it runs `< /dev/null` on purpose, because a bare `localforge` with a tty on stdin opens the interactive session and the installer would never finish. With stdin from `/dev/null` it prints the "type `localforge` to start a session" panel instead (`tests/test_next_step_messaging.py` guards this).

## Conventions

- Pydantic models (`HardwareProfile`, `GPU`, `ModelEntry`) for anything crossing a module boundary; plain dicts/`TypedDict` (`BackendResult`) for backend I/O.
- Tests mock hardware via `HardwareProfile(...)` construction and an inline test catalog (see `tests/test_catalog.py`) rather than patching `detect_hardware()` — keep `catalog.best_match()` pure and test it that way.
- No multi-agent framework dependency by design (see `orchestrator.py` rationale above) — don't reach for LangGraph/AutoGen/CrewAI without revisiting that decision first.
